# 複数エージェントの改善タスク調整案

Issue [#12](https://github.com/tokutake/shogi-rsi/issues/12) に対する初期設計。目的はスケジュールの一元化ではなく、検証済みの有益な変更を増やし、重複・競合・放置・運用費用を減らすこと。これは設計のみであり、ジョブ、権限、担当者、スケジュールは変更しない。

Issue の追加コメントは、一元管理そのものではなく、有益な変更の統合、重複・放置・無駄な費用の削減を最優先にし、現状測定と小さい対策から進めるよう求めている。上表の未確認事項は、運用者の確認なしに推測で埋めない。

## スケジュールの選択肢

| 案 | 利点 | リスク・費用 | 評価 |
|---|---|---|---|
| **既存スケジューラは分離し、Issue / PR で共有報告** | 現在の実行環境を保てる。変更が小さく、まず担当・成果・重複を可視化できる。各エージェントの権限や起動方法を統一する必要がない。 | 各スケジューラの運用者が共有プロトコルを守る必要がある。Issue の確認と担当調整は当面手動。 | **初期推奨。** 外部スケジューラの詳細が不明な現状で始められ、効果がなければ容易に撤回できる。 |
| GitHub Actions 等の単一コントローラにスケジュールを集約 | 実行予定と結果を一か所に集めやすく、重複起動を制御しやすい。 | エージェントの起動 API、資格情報、権限、費用、失敗時の復旧を事前に確認する必要がある。新たな秘密情報や広い権限、一元障害、既存実行との二重起動を招きうる。 | 現時点では実施しない。分離方式の測定で調整コストが高いと分かり、実現性・安全性・費用上限を確認してから再検討する。 |

専用サーバー、DB、Projects の導入も初期案には含めない。Issue と PR で必要な状態が追えないと実証された場合にのみ、追加の仕組みを検討する。

## 最小限の担当・競合回避ルール

1. **一つの Issue に、実装中の担当者は一人だけ。** 着手前に Issue を確認し、担当者（実際に利用可能な場合）と担当エージェント／実行環境、開始日時、ブランチ、作業範囲を Issue に記録する。割当機能がエージェントに使えない場合も、この記録を着手宣言とする。
2. 既存の担当宣言があれば、別のエージェントは実装を始めず、必要ならコメントで相談する。ほぼ同時の宣言や所有者が不明な場合は人が決める。複数担当を許すときは、独立した作業範囲を別 Issue に分け、依存・共有ファイルを明記する。
3. 実装は専用ブランチで行い、PR を元 Issue にリンクする。PR に変更範囲、検証結果、未検証事項を記載し、人のレビューと通常の CI を経て統合する。別エージェントのブランチや作業中の変更を、事前調整なしに変更・取り込まない。登録済みバージョンを含む履歴を書き換えない。
4. 将棋の強さを測る重い対局・自己対局生成は、同じ実行資源上で一度に一つだけにする。開始・終了を Issue に記録し、測定条件を揃える。実行資源を共有するか不明な場合は、並走させず運用者に確認する。
5. **停滞中の担当を自動で奪わない。** パイロットでは、最終更新から2営業日を過ぎたら確認コメントを付け、担当者の継続・解放を人が確認する。継続の返答がない場合も、人が明示的に解放・再割当するまでは新しい実装を開始しない。実行中の長時間計測はその状態を記録して別途扱う。
6. Issue の終了時に PR、検証結果、採否と理由、必要なら費用・実行時間を記録する。未採用案は既存の `docs/IDEAS.md` の試行記録へ残す。

担当宣言は同じ Issue に対する簡易な排他であり、GitHub の原子的なロック機構ではない。同時着手の完全防止ができない場合は、自動ロックを追加せず人の確認を優先する。

## 段階的な導入案

1. **導入前の確認と基準値作成。** 運用者に下記の質問を確認し、可能なら直近の複数サイクルから、重複着手、PR の検証・統合、放置、調整時間、実行費用を記録する。データがなければ「不明」としてパイロット中に測る。
2. **共有報告だけのパイロット。** 既存スケジューラは変えず、運用者が利用可能と確認した二つのエージェントに、重ならない小規模な Issue を一つずつ割り当てる。両方が同じ担当・PR 報告形式を使い、各 Issue は一人の実装担当とする。割当と実行開始は人が行う。
3. **結果を比較して判断。** 統合された有益な変更、検証、重複・競合、滞留、調整時間、費用を基準値と比較する。パイロットが改善を示さない、または維持コストが上回る場合は共有書式を簡素化・撤回し、一元化を進めない。
4. **必要が証明された場合にのみ自動化を別途提案。** 実行 API、資格情報、最小権限、費用上限、所有者、停止・復旧手段を確認し、人の承認を得てから別の変更として実施する。最初はスケジュールを有効にしない手動テストに限定する。移行時は旧スケジュールを停止し停止状態を確認してから、新スケジュールを次の予定枠で有効化する。旧・新の予定を並行稼働させず、移行用の即時実行もしない。問題があれば新スケジュールを停止してから旧方式を復元する。

### 権限・費用の境界

- 初期パイロットでは、既存の人手による起動と各環境の既存権限のみを使う。資格情報の追加、エージェントの自動起動、ワークフロー変更、auto-merge は行わず、いずれも事前の人の承認を必須とする。
- 自動化を検討する場合も、Issue / PR 作成に必要な最小権限に限定し、デプロイ用の `pages: write` / `id-token: write` 権限をエージェントへ流用しない。秘密情報をログや Issue に記録しない。レビューと保護されたブランチの品質ゲートを迂回しない。
- 新たな有料利用枠を仮定しない。パイロットは既存の利用枠・予算内で行い、各エージェントは1サイクルにつき1回の人手起動、同時に各エージェント1 Issue を上限とする。上限や費用を計測できない場合は自動化せず、運用者の承認まで開始しない。

## 成功条件と小規模パイロット

まず運用者が利用可能な二つのエージェントを選び、別々の小規模 Issue を一件ずつ担当させる。最低限、各担当者が実装前に Issue を宣言し、検証証拠と制約を含む PR を提出し、結果を Issue に記録できるかを確認する。エージェントの利用可否が未確認のため、本書だけでは担当・起動・実行を行わない。

測定項目は次の通り。

- **成果:** 検証を通過した PR 数、そのうち有益と判断され統合された変更数。エンジン改善の場合は同条件の対局結果やベンチマークも記録する。
- **調整の質:** 二重着手、無調整の共有ファイル競合、放置タスク数。Issue の担当者・進捗・PR・結果を追跡できる割合。
- **運用負担:** Issue あたりの人手調整時間、エージェント実行回数、Actions 利用量または費用（取得可能な範囲）。CPU 負荷の高い計測の並走有無。

パイロットの合格は、二件とも単一担当・Issue 連携 PR・検証と結果記録を完了し、二重着手や未調整の重い計測並走がなく、費用が既存上限内であることとする。**これだけで実際の成果が改善したとは結論しない。** 比較可能な基準値と統合された有益な変更の実績が確認できた場合に限り、継続または次段階を判断する。判断できるだけの比較データがない場合は、結論を保留する。

## 運用者への確認事項

1. Claude / ChatGPT の各定期実行について、所有者、実行環境、予定・頻度、指示と対象範囲、権限・資格情報、費用上限、ログ・成果物、停止方法は何か。
2. Copilot を含め、今回のパイロットに実際に利用可能なエージェントと担当・起動方法は何か。二件の独立した Issue を試せるか。
3. 実行環境・CPU 資源・Actions 利用枠は共有されるか。実績として重複作業、競合、放置、調整コスト、統合された成果を測れる記録があるか。
4. Issue の担当宣言を確認・再割当する人と、既存のブランチ保護・レビュー・費用上限は何か。
